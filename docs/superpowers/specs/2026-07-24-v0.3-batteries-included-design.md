# Embodied Claude v0.3 Batteries-Included Design

## Status

Approved for implementation on 2026-07-24. This design extends the guided
onboarding merged in PR #105 and defines the release gate for `v0.3.0`.

## Goal

Make the default embodied-claude experience small enough to install without
unselected hardware stacks, equally operable from POSIX shells and Windows
PowerShell, and diagnosable through commands that test the runtime rather than
only inspecting configuration files.

The release remains a phenomenal-consciousness candidate architecture. It does
not claim proof of phenomenal consciousness.

## Release Outcomes

A new user must be able to:

1. clone the repository;
2. run one platform-native setup command;
3. install only Core plus explicitly selected capabilities;
4. run one platform-native doctor command;
5. see actionable static diagnostics and optionally probe each configured MCP;
6. start Claude Code with the same EFPF hooks on Linux, macOS, WSL2, and
   Windows native;
7. save and recall a memory without a first-call Windows deadlock; and
8. understand the social interaction loop without reading an exhaustive root
   README.

Maintainers must be able to:

1. run one release verifier;
2. prove the locked workspace on Ubuntu, macOS, and Windows;
3. prove the Core setup and doctor on all three operating systems;
4. publish a tag only when version and changelog agree; and
5. create a GitHub Release from the verified merged commit.

## Scope

### Included

- Profile-aware root dependencies and `uv sync`.
- Explicit extras for cameras, transcription, voice, X, and host temperature.
- POSIX and Windows command wrappers with shared Python implementation.
- Static, live, and machine-readable doctor output.
- Cross-platform Claude Code hook commands using exec form.
- Python replacements for Core hook behavior currently implemented only in
  Bash.
- Windows-safe state paths for interoception and hook scratch files.
- Main-thread memory embedding warmup before MCP stdio begins.
- Sociality v0.3 workflow documentation.
- Root README pruning and links to focused guides.
- Monorepo version policy, changelog, release verifier, OS CI matrix, and
  release workflow.
- Release tag `v0.3.0` and a non-prerelease GitHub Release after merge.

### Deferred

- Installing autonomous heartbeat as an OS service.
- Replacing launchd/cron/Task Scheduler with a cross-platform daemon manager.
- Guaranteeing unsupported hardware drivers on every OS.
- Packaging a standalone GUI installer.
- Publishing each workspace member independently to PyPI.

The existing autonomous heartbeat remains usable and documented, but its
service-manager redesign belongs to a later minor release.

## Alternatives Considered

### A. Add only Windows wrappers

This is the smallest patch, but it preserves unconditional heavyweight
dependencies, shell-only hooks, and a doctor that can report success without
starting a server. It does not satisfy batteries-included operation.

### B. Profile-aware runtime plus cross-platform doctor (chosen)

Keep the single uv workspace and existing Python services. Make the root
project describe Core and optional capability extras, keep wrapper logic thin,
and test the real MCP processes. This addresses the user-visible failures
without introducing another service framework.

### C. Build a full supervisor and global installed CLI

A supervisor could manage MCPs, heartbeat, and upgrades from one process. It
would substantially expand lifecycle, security, and platform-service scope.
That is a useful later project, not a safe `v0.3.0` release requirement.

## Dependency Profiles

The root `[project].dependencies` contains only Core:

- `memory-mcp`
- `desire-system`
- `sociality-mcp`
- `individual-kernel-mcp`

Transitive sociality packages remain workspace members and are installed
through `sociality-mcp` and `individual-kernel-mcp`.

The root `[project.optional-dependencies]` defines:

| Extra | Dependency |
|---|---|
| `camera-usb` | `usb-webcam-mcp` |
| `camera-tapo` | `wifi-cam-mcp` |
| `transcription-whisper` | `wifi-cam-mcp[transcribe]` |
| `transcription-faster` | `wifi-cam-mcp[transcribe-faster]` |
| `voice-voicevox` | `tts-mcp` |
| `voice-elevenlabs` | `tts-mcp[elevenlabs]` |
| `x` | `x-mcp` |
| `system-temperature` | `system-temperature-mcp` |
| `all` | every optional runtime dependency, including both transcription engines |

Tapo video/audio control does not silently install a transcription model.
Transcription requires its own setup option.

`FeatureSelection` is the source of truth for both generated MCP entries and
uv extras. Setup passes the selected extras to one `uv sync --locked` command.
The doctor derives the expected extras from the same selection rules.

Development dependencies remain in the root `dev` group. CI explicitly
installs that group and all extras; a Core setup does not need test tooling.

## Cross-Platform Commands

Python modules continue to own all behavior. Platform wrappers only find the
repository, verify `uv`, and pass arguments through unchanged.

| Purpose | POSIX / WSL2 | Windows PowerShell or cmd.exe |
|---|---|---|
| Setup | `./scripts/setup.sh` | `.\scripts\setup.cmd` |
| Doctor | `./scripts/doctor.sh` | `.\scripts\doctor.cmd` |
| Release check | `./scripts/release-check.sh` | `.\scripts\release-check.cmd` |

All wrappers execute a standard-library Python script with:

```text
uv run --no-project --python 3.13 python <script> ...
```

This makes setup and static diagnostics available before the workspace is
installed. There is no PowerShell execution-policy requirement.

## Doctor

### Modes

`doctor.py` supports:

- default static checks;
- `--live`, which initializes and lists tools from each configured Core MCP;
- `--json`, which emits a stable machine-readable report; and
- `--config PATH`, preserving the existing override.

Human output retains `[ok]`, `[warn]`, and `[error]`. JSON output contains:

```json
{
  "schema_version": 1,
  "platform": "windows",
  "summary": {"ok": 0, "warn": 0, "error": 0},
  "checks": [
    {
      "status": "ok",
      "subject": "server:memory",
      "detail": "initialized and exposed 31 tools",
      "remediation": null
    }
  ]
}
```

Any error returns exit code 1. Warnings do not fail the command. CLI usage
errors retain argparse exit code 2.

### Static checks

The doctor checks:

- Python 3.13 and `uv` availability;
- current lockfile;
- readable `.mcp.json`;
- required Core entries;
- current exec-form hook schema;
- selected package/extras declarations;
- installed selected distributions;
- writable memory, sociality, field, and hook state parents;
- valid social policy;
- selected credentials without printing their values;
- selected external executables such as `ffmpeg`, `mpv`, or `ffplay`; and
- platform limitations with platform-correct remediation commands.

Invalid TOML or JSON must produce a check result, never an uncaught exception.

### Live checks

A focused `scripts/mcp_probe.py` uses the installed MCP Python client. For each
configured server, it:

1. spawns the exact configured command and argument vector;
2. opens an MCP stdio session with a per-server timeout;
3. calls initialize and `list_tools`;
4. requires at least one tool; and
5. closes the process cleanly.

The memory probe additionally invokes a deterministic temporary-database
roundtrip through the store API so the embedding path is exercised. It does
not write to the user's real memory database.

Secrets are inherited from the selected server environment but never included
in output. Live checks do not call cameras, publish to X, speak, or perform
other outward actions.

## Windows Runtime

### Hooks

Claude Code settings use the current exec form:

```json
{
  "type": "command",
  "command": "uv",
  "args": [
    "run",
    "--directory",
    "${CLAUDE_PROJECT_DIR}",
    "--package",
    "individual-kernel-mcp",
    "efpf-hook",
    "user-prompt-submit"
  ]
}
```

Exec form avoids Bash quoting and passes paths containing spaces as one
argument. The settings do not use `$CLAUDE_PROJECT_DIR`.

Core hook behavior currently living in `interoception.sh`,
`auto-recall.sh`, `continue-check.sh`, and `post-compact-recovery.sh` moves
behind Python subcommands. EFPF `UserPromptSubmit` already reads
interoception, desire, social, memory, and previous-field sources directly, so
no ordering dependency is introduced between hooks.

The existing shell files remain as compatibility wrappers where useful, but
Claude Code settings no longer require Bash, curl, jq, sed, or grep.

### State paths

Temporary state uses `tempfile.gettempdir()` unless an explicit environment
override is set. Durable state uses `Path.home() / ".claude"`. No Core Python
path defaults to literal `/tmp`.

### CI

GitHub Actions adds Windows and macOS jobs that:

- install Python 3.13 and uv;
- run `uv sync --locked --all-extras --group dev`;
- check the lock;
- run platform-neutral root tests;
- invoke the native setup wrapper in dry-run mode;
- invoke the native doctor wrapper on a generated Core fixture; and
- validate hook exec form.

Ubuntu remains the full lint, mypy, and package-test job. Windows additionally
runs the memory warmup regression and Core live MCP probe.

Hardware-specific tests remain deterministic and do not require devices or
API keys.

## Memory Startup

`E5EmbeddingFunction` gains a public idempotent `warmup()` method.
`MemoryStore.warmup()` delegates to it synchronously.

`MemoryMCPServer.connect_memory()` calls `warmup()` on the main thread before
SQLite connection work or MCP stdio thread activity. This prevents the first
`remember` call from importing SentenceTransformer, scikit-learn, and SciPy in
an anyio worker thread on Windows.

The setup model download remains useful for network predictability, but it is
not the concurrency fix. Tests prove:

- warmup is idempotent;
- server startup warms before asynchronous connection;
- encode calls reuse the warmed model; and
- startup failure reports a model-loading error rather than hanging.

## Sociality Documentation

`sociality-mcp/README.md` leads with the v0.3 operational loop:

```text
compose_interaction_context
-> plan_response
-> act
-> record_agent_experience
-> record_interpretation_shift (when interpretation changes)
```

It distinguishes mandatory post-response experience recording from optional
interpretation shifts, documents the current field input, and links to focused
tool references. This resolves issue #102.

The root READMEs remain outcome-first. Exhaustive EFPF research detail,
autonomy/heartbeat operation, tool inventories, and release procedures live in
focused documents under `docs/` or package READMEs.

## Version and Release Policy

The repository uses one product release version: `0.3.0`. Workspace package
versions are aligned for repository releases even though packages are not yet
published independently.

`CHANGELOG.md` follows Keep a Changelog headings and includes an unreleased
section plus `0.3.0`. Technical language uses “phenomenal-like causal
architecture” or “phenomenal-consciousness candidate architecture”.

`scripts/release_check.py` verifies:

- root and workspace package versions equal the expected version;
- runtime `__version__` and default MCP server versions agree where present;
- `CHANGELOG.md` contains that version and release date;
- `uv.lock` is current;
- the working tree is clean when `--require-clean` is used; and
- an optional `--tag v0.3.0` matches the version exactly.

The release workflow triggers on `v*` and:

1. checks out the tagged commit;
2. installs all extras and dev tools from the lock;
3. runs release verification;
4. runs the deterministic release test suite;
5. builds a source archive manifest; and
6. creates a GitHub Release with the matching changelog section.

The workflow never creates a tag. The maintainer process is:

1. merge the green release PR;
2. update local `main` to the exact merged commit;
3. run the release verifier with `--require-clean --tag v0.3.0`;
4. create and push annotated tag `v0.3.0`;
5. wait for the release workflow; and
6. verify the public GitHub Release and attached source archives.

## Test Strategy

Every behavior change follows red-green-refactor.

Required deterministic coverage:

- dependency selection maps to exact uv extras;
- Core excludes camera, transcription, voice, X, and temperature packages;
- transcription is never implied by Tapo camera selection;
- setup executes exactly one selected-profile sync;
- POSIX and Windows wrappers preserve arguments and exit status;
- static doctor errors, warnings, JSON schema, and remediations;
- invalid policy/config produces a result rather than an exception;
- live probe success, timeout, empty tool list, and redacted failure;
- all Claude Code hooks use exec form and no Core hook requires `.sh`;
- temporary paths are platform-derived;
- Windows memory warmup ordering and first-call regression;
- sociality documentation contains the v0.3 loop;
- version/changelog/tag consistency; and
- release workflow permissions and tag-only trigger.

Release verification includes:

```text
uv lock --check
uv run --all-extras --group dev ruff check .
uv run --all-extras --group dev mypy memory-mcp/src/memory_mcp/
all package and root pytest suites
Core setup/doctor in a clean archive
Core live MCP probe on Ubuntu and Windows
```

## Acceptance Gate

`v0.3.0` is releasable only when:

- a clean Core install does not resolve Whisper or faster-whisper;
- selected capability installs and generated MCP entries agree;
- Windows uses native setup and doctor commands;
- Core hooks run without Bash-specific syntax;
- the Windows memory regression is covered and green;
- doctor static and live modes are green for Core;
- Ubuntu, macOS, and Windows CI are green;
- all lint, mypy, root tests, and package tests pass;
- issue #99 and #102 are addressed by code/docs evidence;
- the release PR is merged;
- the annotated `v0.3.0` tag points to the merged commit; and
- the non-prerelease GitHub Release is published successfully.
